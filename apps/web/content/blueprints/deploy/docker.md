# Containerize your Dawn app with Docker

You are an AI coding agent preparing a Dawn app for self-hosting with the `node` build target. Dawn generates the production server and its hardened Dockerfile. Use those artifacts directly; do not hand-author a competing Dockerfile.

## Prerequisites

Confirm these prerequisites before changing the app:

1. **Node.js 24 or newer** — Dawn packages require Node >=24:

   ```bash
   node --version
   ```

   If the reported major is below 24, switch or upgrade Node before continuing.

2. **Docker** — confirm the daemon tooling is installed:

   ```bash
   docker --version
   ```

   If Docker is unavailable, install it from [docker.com/get-started](https://www.docker.com/get-started/) before building the image.

3. **Project conventions** — detect the package manager from the lockfile, read `AGENTS.md` when present, and inspect `dawn.config.ts`, `package.json`, `.dockerignore`, and any existing root `Dockerfile`.

## Keep the CLI at runtime

The emitted `.dawn/build/server.mjs` imports `@dawn-ai/cli` when the container starts. Ensure `package.json` lists `@dawn-ai/cli` under `dependencies`, not only `devDependencies`; the generated image installs production dependencies and strips dev-only packages.

Use the project's package manager to move or add the existing compatible Dawn version, for example:

```bash
pnpm add @dawn-ai/cli
# npm install --save @dawn-ai/cli
# yarn add @dawn-ai/cli
```

Preserve the app's existing version range or workspace specifier when moving the dependency.

## Select the Node target

Merge this target selection into the existing `dawn.config.ts` rather than replacing unrelated configuration:

```ts
import { config } from "@dawn-ai/cli"

export default config({
  // Keep the app's existing settings here.
  build: { targets: ["node"] },
})
```

Naming `build.targets` replaces the default target list. `['node']` asks Dawn only for the self-hosted Node runtime artifacts.

## Verify and build

From the app root, run the current verification workflow and regenerate a clean build:

```bash
pnpm exec dawn verify
pnpm exec dawn test
pnpm exec dawn build --clean
```

Use `npx dawn ...` or `yarn dawn ...` equivalents when that is the project's package manager. Fix failures before building an image.

The Node target emits:

- `.dawn/build/server.mjs` — the production entry point that boots the Dawn HTTP runtime.
- `.dawn/build/modules.mjs` — the static route, tool, state, memory, and middleware module manifest generated from the app.
- A generated Dockerfile containing Dawn's authoritative marker:

  ```text
  # Generated by dawn build (node target). Safe to edit; delete to regenerate.
  ```

Dockerfile placement is marker-aware:

- With no root `Dockerfile`, Dawn writes the generated file at `./Dockerfile`.
- If the root file still contains Dawn's generated marker, the next build refreshes it in place.
- If the root file is user-authored or the marker was removed, Dawn preserves it and writes the generated file to `.dawn/build/Dockerfile`.

Do not add an older blueprint marker or manually recreate the generated contents. Dawn's marker above is the only marker that controls refresh behavior.

## Keep the build artifact in the Docker context

The generated Dockerfile copies the host-built `.dawn/build/` directory into the image; it does not rerun `dawn build` inside the container. Make sure the app root is the Docker build context and that `.dockerignore` does **not** exclude `.dawn`, `.dawn/build`, or `server.mjs`.

It is safe and recommended to exclude local dependencies, source-control data, and secrets while retaining `.dawn/build`:

```text title=".dockerignore"
node_modules
.git
.env
.env.*
coverage
```

Review an existing `.dockerignore` rather than overwriting it. Remove any broader `.dawn` rule before building.

## Build the emitted Dockerfile

Use the path Dawn actually emitted. After `dawn build --clean`, this shell snippet selects the marked root file or the preserved-user-file fallback and verifies it exists:

```bash
DAWN_DOCKERFILE=Dockerfile
if ! grep -Fq '# Generated by dawn build (node target). Safe to edit; delete to regenerate.' "$DAWN_DOCKERFILE" 2>/dev/null; then
  DAWN_DOCKERFILE=.dawn/build/Dockerfile
fi
test -f "$DAWN_DOCKERFILE"
docker build --file "$DAWN_DOCKERFILE" --tag my-dawn-app .
```

Keep `.` as the final build-context argument even when the Dockerfile lives under `.dawn/build/`; its `COPY` instructions are rooted at the app.

The generated image is a single-stage `node:24-slim` image. It installs production dependencies, copies the app and `.dawn/build`, changes ownership to UID/GID `1000:1000`, runs as that non-root user, exposes port `8000`, checks `/healthz`, and starts `.dawn/build/server.mjs`.

## Pass secrets at container run time

Never bake provider keys, database credentials, or other secrets into the image. Keep secret files out of the Docker context and inject values when the container starts:

```bash
docker run --rm \
  --publish 8000:8000 \
  --env-file .env \
  my-dawn-app
```

The Node runtime reads its environment at run time. Document required keys in a safe `.env.example`, but do not commit populated secret files.

In another terminal, smoke-test the generated health endpoint:

```bash
curl --fail http://127.0.0.1:8000/healthz
```

Then exercise one application route through Agent Protocol or AG-UI to validate model credentials, stores, and route wiring—not only process health.

## Replica and persistence limits

The default checkpointer, threads store, permissions store, and memory store are local to the container's filesystem. Even when durable stores are configured externally, the one-run-per-thread gate and cancellation registry are process-local.

Run one replica unless the deployment guarantees thread-keyed sticky routing to the same process **or** supplies distributed per-thread serialization and cancellation routing. Without one of those guarantees, concurrent runs and cancellation requests for the same thread can reach different replicas and bypass Dawn's in-process coordination.

Mount durable storage or configure external stores when thread state must survive container replacement. External persistence alone does not solve the run/cancel coordination requirement.

## Updating an existing install

1. Confirm Node >=24 and keep `@dawn-ai/cli` in `dependencies`.
2. Run `dawn verify`, `dawn test`, and `dawn build --clean` again.
3. Let the generated marker decide placement: Dawn refreshes its marked root Dockerfile and preserves an unmarked user file by emitting `.dawn/build/Dockerfile`.
4. Confirm `.dawn/build` remains in the build context.
5. Rebuild using the actual emitted path and repeat the `/healthz` plus route smoke tests.
