# v0.8.22 Terminal Recovery Design

## Status

Approved design, 2026-09-03. Sub-project B of the v0.8.22 unblock. Sub-project
A (controller draft visibility) and the v0.8.23 Version Packages merge are out
of scope and are sequenced after this work.

## Problem

The v0.8.22 candidate (commit `2a80deece2ff958fe7fde8fddeb4f99bed70a1c8`,
immutable annotated tag `v0.8.22`) is escrowed in draft Release `379991871`
with a canonical `ESCROWED` marker and 45 base assets. Two duplicate drafts
(`379982100`, `379986168`) were quarantined on 2026-09-03 by the reviewed
duplicate-draft recovery command; the canonical draft is the sole marker-backed
candidate.

The candidate cannot be published by its own workflow. Two production dispatches
on 2026-09-03 (runs `33764298343` and `33779071325`) proved that the Actions
`GITHUB_TOKEN` with `contents: read` receives HTTP 403 for every draft Release
and lists no drafts (probe run `33780657483`). `detect`, `publish-npm`, all five
smoke lanes, `dispatch-audit`, and the audit workflow's `verify-draft` job run
with `contents: read`, and for v0.8.22 those permissions are fixed by the
workflow file at the immutable tag. No change on `main` alters that run.

The candidate also cannot be abandoned. The 2026-08-25 design disabled workflow
abandonment; the dormant `abandon` command requires an independent reviewer's
approval on a protected `release-abandonment` environment captured from a
workflow run, which a single-owner repository cannot produce, and the observer
only accepts tombstones bound to that environment. The design states that a
disabled-era candidate that becomes irrecoverable is "permanently
non-abandonable under this workflow" and that terminal recovery needs "a
separate reviewed design". This document is that design.

Without a terminal state, `planRelease` keeps reporting
`older-tagged-candidate-incomplete` for every newer candidate, so v0.8.23 can
never proceed.

## Goals

- Make v0.8.22 terminal (`ABANDONED_PREPUBLICATION`) in a way the controller on
  `main` can observe regardless of what its GitHub token can see.
- Keep the authority model as rigorous as the duplicate-draft recovery: a
  reviewed merged commit, an authenticated operator, an edit freeze,
  compare-before-write mutations, and independent verification.
- Keep GitHub and git in agreement: the canonical draft carries the same
  tombstone that git records.
- Preserve the immutable tag, the 45 escrow assets, and both quarantined
  duplicates exactly as they are.
- Leave the existing environment-based abandonment path untouched.

## Non-goals

- Publishing v0.8.22 in any form. npm never receives 0.8.22.
- Deleting, moving, or reusing the `v0.8.22` tag or any Release.
- Giving the controller visibility of drafts (sub-project A).
- A reusable abandonment tool. The writer is pinned to v0.8.22 and is deleted
  after the release train moves on.
- Changing the protected environment path or its tests.

## Decisions

Each decision below was chosen over its alternatives during design review.

1. **Authority: reviewed-commit authority, not an environment reviewer.** The
   human approval is the review and merge of the pull request that commits the
   terminal record. The operator command runs only from a clean clone at a
   merged commit whose `CI / validate` succeeded, exactly like
   `recover-v0.8.22-duplicate-drafts.mjs`.
2. **Medium: a git-resident terminal record is the authority.** A draft-only
   tombstone is invisible to the controller at `contents: read`, so it would not
   unblock v0.8.23 until sub-project A lands. A published immutable Release
   would create a public release page for a version that never shipped. The
   record lives in the repository, is reviewed like any change, and is
   immutable through history.
3. **GitHub is stamped to match git.** The canonical draft's body is replaced
   with the existing abandonment body format and `abandonment.json` is uploaded,
   so once drafts become visible the observer cross-checks rather than needing a
   precedence rule.
4. **General reader, pinned writer.** The observer and planner learn one rule
   for any committed record. Only the command that produces and applies the
   v0.8.22 record is pinned, and it is removed afterwards.

## Architecture

Three pieces, in dependency order.

### 1. Terminal-record store (general)

New module `scripts/release/terminal-record-store.mjs`.

- `readTerminalRecord({ git, ref, version })` reads
  `scripts/release/terminal-records/v<version>.json` from the candidate
  checkout through the existing git reader (`showFile`), returns `null` when
  the file is absent, and throws a typed error when it is present but invalid.
- `parseTerminalRecord(bytes)` validates the schema below with exact field sets
  at every level, digest and SHA patterns, and a 512 KiB byte cap.
- `canonicalTerminalRecordBytes(value)` produces sorted-key JSON with one
  trailing newline. A record must equal its own canonical bytes.

The store is consulted by `observeProductionCandidate` at the point where the
immutable inventory is read, from the same checkout, before any GitHub read
for that version.

### 2. Observer and planner integration

Rules, evaluated in order for the observed version:

1. **Record present and valid.** The version observes as
   `release.status: "abandoned"`, marker phase `ABANDONED`,
   `abandonment.recorded: true`, state `ABANDONED_PREPUBLICATION`,
   `disposition: noop` (the planner's disposition for terminal states). No
   GitHub read is required for this classification.
2. **Record present and the draft is visible.** The draft must match the
   record: same numeric Release ID, body parsing to the same tombstone,
   `abandonment.json` asset with the record's digest and size, and the 45 base
   assets unchanged in name, ID, and digest. Any mismatch is reported as an `AMBIGUOUS` diagnostic with code
   `TERMINAL_RECORD_MISMATCH` (source `github`), which the planner already
   turns into the blocking conflict `production-observation-ambiguous`. The
   observer also marks the release observation ambiguous so the planner itself
   blocks, not only the CLI's diagnostic gate. A record whose own identity does
   not name this candidate is reported as `TERMINAL_RECORD_FOREIGN` with the
   same consequences as a mismatch.
3. **Record present and the draft is invisible.** Allowed; the record alone is
   authoritative. This is the controller's situation until sub-project A.
4. **Record present and npm shows the version for any package.**
   `AMBIGUOUS` diagnostic `TERMINAL_RECORD_PUBLISHED_VERSION` (source `npm`),
   blocking through `production-observation-ambiguous`; a record can never mask
   a publication. Known limitation: the independent-audit and post-publication
   audit jobs check out the candidate tag, whose tree predates any record on
   `main`, so this rule cannot fire on those paths. The same holds for the
   dormant protected-abandonment handoff, which is disabled and must gain an
   explicit ref if reactivated.
5. **No record.** Behavior is unchanged for every existing state.

A record that fails validation blocks the whole observation rather than being
ignored; a malformed terminal record is treated as a tampering signal.
Concretely, the observer emits `TERMINAL_RECORD_INVALID` and marks the release
observation ambiguous. A record that exists but cannot be read from git at all (transport,
timeout, output cap) is reported as `TERMINAL_RECORD_UNREADABLE` with the same
consequences, so an operator can tell a bad file from a bad runner.

`mapProductionAbandonmentRelease` keeps its environment-based path unchanged.
The record path is a sibling branch chosen only when a record exists.
`planRelease` needs no change: `ABANDONED_PREPUBLICATION` is already terminal
for arbitration (`terminalHistoricalState`) and `noop` for disposition, so
a newer candidate stops seeing `older-tagged-candidate-incomplete`.

### 3. Operator command (pinned)

New script `scripts/release/abandon-v0.8.22-candidate.mjs`, sharing
`duplicate-draft-recovery-adapters.mjs`, the private-path rules under
`.dawn/release-recovery/`, the literal
`--acknowledge-non-atomic-release-edit-freeze` flag, receipt conventions, and
the reviewed-commit checks of the duplicate-draft recovery command.

`capture --reviewed-commit <sha> --reason <text> --output <path>` is read-only.
It verifies that the reviewed commit is the merge commit of exactly one merged
pull request into `main` whose `CI / validate` succeeded at the reviewed head
and whose tree equals the reviewed head tree. It reads the annotated tag object
and peel, the canonical draft by numeric ID with the operator token, its body
and 45 assets, both duplicate recovery receipts, npm for all 21 packages twice
at least 60 seconds apart, and the complete Release-run inventory for the
candidate SHA with every `publish-npm` job proven never started. It refuses
unless the draft is exactly the `ESCROWED` canonical identity captured on
2026-09-03. It writes the canonical record to a private mode-`0600` path. The
operator copies that file to `scripts/release/terminal-records/v0.8.22.json`
and opens the record pull request.

`apply --record <path> --reviewed-commit <sha>
--acknowledge-non-atomic-release-edit-freeze --output <path>` requires the
reviewed commit to be the record pull request's merge commit and the record at
that commit to equal the file on disk byte for byte. It re-captures fresh
evidence and requires equality with the record's evidence except for
timestamps. It then mutates with compare-before-write only:

1. Upload `abandonment.json` only when absent; if present it must match the
   record's digest and size.
2. Patch only the body through `updateDraftReleaseIfCurrent`, keyed on the
   captured body digest, to the existing abandonment body format containing the
   `ABANDONED` marker and the embedded tombstone.
3. Re-read the draft by ID and require the body to parse to the record's
   tombstone and the asset set to be the 45 base assets plus `abandonment.json`.
4. Run the normal production observer and require `ABANDONED_PREPUBLICATION`,
   `noop`, no conflicts, no diagnostics.
5. Write the local write-once final receipt.

Resumability follows a three-state ladder classified from fresh reads:
`escrowed` (original marker body, 45 assets) → `asset-uploaded` (original body,
45 assets plus the exact tombstone asset) → `abandoned` (tombstone body, 46
assets). A rerun performs only the missing transition. Any other state is a
conflict, never a repair opportunity.

## Terminal record schema

`scripts/release/terminal-records/v0.8.22.json`, canonical JSON.

- `schemaVersion`: `1`.
- `kind`: `"abandoned-prepublication"`.
- `version`: `"0.8.22"`; `commitSha`: the candidate SHA.
- `tag`: `{ name, objectSha, commitSha }` for the annotated tag and its peel.
- `reason`: the operator's stated reason, bounded plain text.
- `predecessor`: reuses the existing tombstone predecessor shape:
  `state: "CANDIDATE_ESCROWED"`, `releaseId`, `releaseStatus: "draft"`,
  `bodySha256`, `marker` (phase `ESCROWED`, `manifestSha256`,
  `releaseRecordSha256`, `baseAssetSetSha256`, `attestationSet`).
- `evidence`: `escrowAssets` (the 45 base assets as `{ id, name, sha256 }`,
  whose names must equal the marker's attestation subjects and bundles plus
  `release-record.json`), `npm` (two observations of all 21 packages, each
  absent, with `observedAt` at least 60 seconds apart), `releaseRuns` (every
  terminal run for the candidate SHA with `publishJobStarted: false` per
  attempt), and `duplicateRecovery` (both duplicate Release IDs, their
  recovery receipt asset IDs and digests, and the final authorization receipt
  digest).
- `authority`: `{ mode: "operator-recovery", operator, capturedAt,
  reviewedCommit }`, where `reviewedCommit` is the merge commit of the code
  pull request the capture ran from. The record cannot contain its own merge
  commit; git history is that proof.
- The record file's canonical bytes ARE the tombstone: the same bytes are
  uploaded as `abandonment.json` and their SHA-256 is the marker's
  `abandonmentSha256`. There is no nested `tombstone` field.

Validation rejects unknown keys, malformed digests, a `commitSha` that differs
from the tag peel in the current checkout's history, and any record for a
version with a published npm package.

## Error handling

The command exits without mutation on every unexpected live state, never
retries an ambiguous write, and uses exit code 3 to mean output cleanup is
uncertain. The operator freeze remains until independent verification passes.
The observer turns a malformed record into a blocked observation and a
published-but-recorded version into a permanent conflict, because unpublishing
is forbidden.

## Testing

All under `pnpm test:release-controller`.

- Schema round-trips and strict rejections: unknown keys, digest patterns, byte
  cap, tag-peel mismatch, published-package refusal.
- Observer tests with the rehearsal fake GitHub for each rule: draft invisible,
  draft visible and matching, draft visible and tampered (body, asset, base
  asset), npm published, malformed record.
- Planner test: a newer candidate is not blocked by a recorded older version and
  is still blocked by an unrecorded one.
- Command tests with mocked adapters: capture, each apply transition, resume
  from each ladder state, evidence drift, reviewed-commit mismatch, record
  mismatch.
- Workflow-contract pins: the new script and the record directory join the
  entrypoint allowlist and `release-script-hashes.json`, and
  `STARTING_SCRIPT_PIN_SHA256` moves with a comment.
- Mutation checks on review findings: delete a guard, confirm a test goes red.

## Production sequence

1. **PR 1** (code): store, observer and planner wiring, command, tests,
   runbook section. Merge on green `validate`.
2. **Operator `capture`** from a clean clone at PR 1's merge commit, under the
   runbook's freeze and same-principal checks. Produces the record.
3. **PR 2** (record only): commits `scripts/release/terminal-records/v0.8.22.json`.
   Its review is the approval. Merge on green `validate`.
4. **Operator `apply`** from a clean clone at PR 2's merge commit.
5. **Independent verification**: enumerate Releases with pagination, re-read all
   three by ID, download `abandonment.json` by numeric asset ID, hash it against
   the record, run a local `observe` at PR 2's merge and require
   `ABANDONED_PREPUBLICATION` / `noop` / no conflicts, then release the
   freeze and record the ledger row.
6. Sub-project A, then Version Packages PR #525 for v0.8.23, then a cleanup
   pull request deleting both one-time recovery commands.

## Success criteria

- A local `observe` at PR 2's merge reports v0.8.22 as
  `ABANDONED_PREPUBLICATION`, `noop`, `conflicts: []`,
  `diagnostics: []`.
- Draft `379991871` carries the abandonment body and `abandonment.json`, and its
  45 base assets are unchanged in ID, name, and digest.
- npm has no 0.8.22 for any of the 21 packages.
- Tag `v0.8.22` and both quarantined duplicates are unchanged.
- A simulated 0.8.23 candidate plans without
  `older-tagged-candidate-incomplete`.
